# 输出约定与字段字典

版本：`1.0.0`。Schema 版本：`1.0.0`，使用 JSON Schema Draft 2020-12。所有 JSON 使用 UTF-8，字段区分大小写。本文件中的时间、代号及片段示例均为虚构演示，不构成行动建议。

## 两个阶段

**阶段一 `information_organization`**：输出已确认事实、推测、未知、矛盾与待确认项，暂不评价行动。`timeline` 为 `[]`，`keyTurningPoint`、`reusableRule` 为 `null`；事实清单保留事件引用与时间，不输出隐含推荐。

**阶段二 `action_analysis`**：输出结构化时间轴、指定行动的选项比较、一个关键转折点、一条条件性修正规则，以及最多三个关键缺失信息。缺乏依据的转折点或规则用 `null`，并在 summary 中解释。事实、解释和建议分区展示。

两阶段均输出 `analysis.json`（工具读取）及 `summary.md`（用户阅读），首次放在 `results/<taskId>/`。状态显式写 `pending_review`；用户复核前不得擅自标为接受。已有结果保留，后续用成对的修订文件名，并在 summary 记录前版文件、阶段、修订原因与依据。

## 时间与空值

| 表示 | 结构与含义 |
| --- | --- |
| 精确时间 | `{"kind":"exact","seconds":318}` |
| 时间区间 | `{"kind":"interval","startSeconds":310,"endSeconds":318}`，两端均包含，起点不晚于终点 |
| 未知 | `{"kind":"unknown"}`，不得附加时间值 |

秒数为非负数，可以含小数，均相对于任务约定的同一起点；T001 的 `00:00` 为演示计时起点，`05:18 = 318` 秒。未知边界不编造；只有单侧界限时，时间对象用 unknown，界限写入待确认说明。Schema 约束各 kind 的字段，但区间起止大小和发生/获知关系另行检查。

必填字段不隐式省略。`null` 表示单一引用或结构当前未知/未配置；`[]` 表示当前没有已提供的条目，不代表客观上不存在；不得以空字符串替代未知。Schema 的 `default` 是提示，校验器不会负责填充，写出文件时应显式提供。非空文字字段不能仅有空白。

## 共用结构

- `richText` 为非空的类型化片段数组：`[{"type":"entity","ref":"A0"},{"type":"text","text":"可以考虑转向"},{"type":"entity","ref":"L1"}]`。能力引用用 `{"type":"capability","ref":"K3"}`。涉及对象或能力的自由说明使用引用片段；普通说明用 text 片段。不输出真实名称。
- ID 与引用使用中性代号；`actorRef`、`locationRef`、`typeRef`、`ownerRef` 允许 `null` 的含义以各字段为准。`targetRefs` 与 `evidenceEventRefs` 是去重的 ID 数组，空数组表示未提供对象/证据。
- `claim`：`content` 为 richText，`evidenceEventRefs` 指向输入事件，`asOf` 为信息截止时间。已确认事实、推测与未知靠所在数组区分。`asOf` 未知不允许据此评价具体历史节点。
- `actionOption`：`action` 为 richText，`actorRef` 可空，`targetRefs` 为对象数组，`locationRef` 可空；`prerequisites`、`costs`、`expectedEffects`、`stopConditions` 为 richText 数组，`rationale` 为简明 richText，`evidenceEventRefs` 为依据。缺少条件时明确写“未知/待确认”，不得凭空填收益。选项的四个条件类数组至少各一项。

## entities.json

顶层必填 `schemaVersion`、`entities`、`capabilities`、`rules`。

- 对象必填 `id`、`category`、`side`、`neutralLabel`、`description`、`entityKind`、`typeRef`、`ownerRef`、`locationRef`。description 为 richText；其余说明标签为非空字符串。`entityKind` 区分角色、类型和实例；`typeRef` 只指向类型，`ownerRef` 指所有者，`locationRef` 指已配置位置，未知均为 null。对象表是引用注册表，不证明其已出现。
- `category`：`actor`、`role`、`collaborative_unit`、`channel`、`defensive_node`、`resource_unit`、`advancing_unit`、`status`；`side`：`A`、`B`、`neutral`、`unknown`、`not_applicable`。角色与具体身份无默认绑定。
- 能力必填 `id`、`ownerRef`、`neutralLabel`、`description`、`configurationStatus`、`parameters`。ownerRef 必须指向所属对象；`configurationStatus` 为 `initial_abstract_model`、`configured`、`unknown` 或 `unconfigured`。参数条目含 `name`、`status`、`value`、`unit`：status 为 configured 时 value 为数值或非空文字，unknown/unconfigured 时 value 为 null；unit 未配置为 null。不写未提供的参数值。
- 规则条目必填 `id`、`status`、`source`、`description`，可记录 configured/unknown/unconfigured；source 为 initial_abstract_model 或 task_configuration。未知机制不因此被补成默认机制。

## events.json

顶层必填 `schemaVersion`、`events`。每个事件必填：

| 字段 | 含义 |
| --- | --- |
| eventId | 唯一事件 ID |
| occurredAt / knownAt | 发生时间 / 对分析主体可用时间，均为 time 对象 |
| sequenceIndex | 非负整数，稳定的材料排列序号，不替代时间 |
| actorRef / targetRefs / locationRef | 行为主体（未知为 null）、涉及对象、位置（未知为 null） |
| action | richText，材料中的行为或信息陈述 |
| stateChanges | 状态变化数组；条目含 subjectRef、attribute、before、after、knowledgeStatus |
| observationStatus | input_fact / hypothesis / unknown，分别表示输入明述 / 推测 / 未知，不代表外部真实性已验证 |
| relatedEvidence | 证据数组，条目含 evidenceId、sourceLabel、excerpt；excerpt 为 richText |
| unresolvedItems | 待确认数组，条目含 id、question（richText）；无已列问题用 [] |

stateChanges 的 before/after 为 richText 或 null；null 是该值未知。knowledgeStatus 与 observationStatus 共用三种状态。字段 attribute 为中性属性标签；同一事件可记录多个对象状态。未知值不能因列表为空被认定为正常状态。

## manifest.json

必填 `taskId`、`schemaVersion`、`contextVersion`、`entityFile`、`eventFile`、`requestFile`、`relatedCaseIds`、`inputStatus`。本工作区不另建 manifest Schema；这些字段另行检查。文件名相对于任务目录；案例编号通过 `cases/INDEX.md` 定位。`inputStatus` 为 pending_check / needs_confirmation / confirmed，默认 pending_check，未经用户确认不自动升级为 confirmed。

## analysis.json

必填 `schemaVersion`、`analysisId`、`taskId`、`status`、`stage`、`inputFacts`、`hypotheses`、`unknowns`、`conflicts`、`timeline`、`keyTurningPoint`、`reusableRule`、`missingInformation`。四种事实整理数组均使用 claim；conflicts 也包括待确认输入问题。status 为 pending_review / needs_revision / reviewed_accepted / reviewed_rejected；后两者只记录用户明确反馈。

timeline 每项含：

- `eventRef`：对应输入事件；`decisionAt`：判断节点；`knowledgeCutoff`：比较选项共用的信息截止时间。
- `knownState`：当时可知状态的 claim 数组，不能放入之后获知的证据。
- `behaviors`：双方行为，条目含 side、actorRef、action（richText）、evidenceEventRefs；意图只放在 hypotheses 中。
- `conditionChanges`：条件变化 claim 数组；解释不得冒充输入事实。
- `actualAction`：实际行为的 richText，未提供为 null；实际行为不因被记录就获得推荐。
- `alternatives`：actionOption 数组；只在用户指定比较的节点列选项，其他节点允许 []。
- `laterFeedback`：条目含 eventRef、knownAt、updateTrigger（richText），专门保存后续反馈。不得被同项 knownState 或选项依据提前引用。

`keyTurningPoint` 为 null 或单个对象：eventRef、asOf、conditionChange、whyItMatters、evidenceEventRefs。`reusableRule` 为 null 或单个对象：condition、action、stopConditions、limits、evidenceEventRefs、reviewStatus；reviewStatus 固定 pending_review，不自动成为背景规则。上述文字均用 richText，stopConditions 与 limits 为 richText 数组。`missingInformation` 最多三项，每项含 question、whyItMatters（richText）；全部未知仍可列在 unknowns，不受三项限制。

## 校验边界

三个 Schema 中的共用定义保持一致且内嵌，无外部网络依赖。它们只校验结构；还需单独检查 ID 唯一性、引用存在性与类型、事件排列、时间区间、发生/获知关系、证据是否当时可用、片段是否正确使用、理由是否有依据。Schema **不能验证结论正确**，也不代表执行了场景操作。
